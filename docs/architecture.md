# Architecture — full reference

> **Read on demand.** The always-loaded contract is `.claude/rules/architecture.md`,
> one short entry per invariant. This file is the full text of each rule: the
> reasoning, the measurements and the incidents behind it. **Numbering is shared
> with the rules file and permanent** — code comments cite `invariant #N`.
> When a rule changes, change it in both places.

## Critical Invariants (DO NOT BREAK)

Qualification: A rule belongs here if (1) violating it breaks the system in non-obvious ways, (2) it's not self-evident from the code, and (3) it applies codebase-wide.

1. **System audio is ScreenCaptureKit and NOTHING else — failing loudly beats recording silence**: `resolveSystemCaptureMethod()` (`services/recorder.js`) has one success case and three throws, each naming a single specific fix: helper binary missing → `npm run build:native`; grant refused → System Settings > Screen Recording; otherwise → requires macOS 13+. There is deliberately **no fallback**. Recording refuses to start rather than beginning a session that cannot capture the other side.
   - Why: the removed sox+BlackHole fallback could not fail loudly. BlackHole is a **cable, not a source** — it carries audio only when system output is routed into it via a Multi-Output Device, manual configuration the app can neither perform nor verify (the old check regexed a device *name*, which was wrong in both directions). Its failure mode was a correctly-sized, digitally-silent WAV discovered after the meeting. Measured over 58 sessions it engaged once and lost that meeting entirely; it never once captured successfully. A refusal costs seconds, a silent recording costs the meeting.
   - **Mid-flight, warn — never switch.** SCK can start cleanly and deliver nothing (gotcha #5), so `watchSckStartup` polls for real bytes and after `SCK_START_TIMEOUT_MS` (8s) fires `onNoAudio`, which **warns and keeps recording**: it marks the track `silent`, emits `sckSilentWarning()` naming the live output device, and leaves the mic track running. It used to swap capture methods here, which is how a *healthy but slow* SCK became a lost meeting under the old 3s timeout. Killing a working capture to chase a fallback is strictly worse than reporting the problem.
   - **Proof of signal, not proof of growth.** This invariant has always said a capture path "must be able to *prove* it is capturing real audio". It could not: every check in the system measured whether the file was GROWING, and a zero-filled WAV grows at exactly the byte rate of speech, so no growth check can ever fail (gotcha #16). Implemented 2026-08-14 by measuring samples — `LevelMonitor._readPeak` (tri-state; `null` is unreadable and is **never** evidence of silence) feeding `services/signalWatcher.js`, plus `measureWavPeak` over every sample at processing time. A verdict requires the system track to have produced nothing *while the mic has proven signal*; that corroboration is what separates a dead capture from "nothing is playing yet", which are otherwise identical. `health` (is the file growing) and `signal` (is it audio) are independent, and the pair that lost three meetings is `health: 'live'` with `signal: 'silent'`. **The PASSIVE half of this covers DUAL-track recordings only.** The corroboration that makes an inferred verdict trustworthy is also what limits it: with one track there is nothing to corroborate against, so `SignalWatcher` never fires in system-only mode. Since 2026-08-17 that is no longer the whole story — see invariant #23: an active probe needs no corroboration, so verification at recording start covers BOTH modes.
   - **Proof beats inference, and the probe is how you get proof.** Everything above still WAITS to see whether audio turns up and reasons about the silence. `services/captureProbe.js` + `services/probeRunner.js` play a known two-tone signature through the machine's own output and look for exactly it in the captured samples, which collapses the ambiguity the passive path can only bet on. Invariant #23.
   - **The filter shape is `excluding`, and it is measured rather than reasoned about.** The per-app `.including` filter, added as the fix for gotcha #5, records digital silence on this machine — see gotcha #15 for the head-to-head numbers. Which shape works has now changed twice, so the helper carries `--filter-shape` to A/B it in situ. It is a diagnostic and is never selected automatically: a silent alternate path is exactly what this invariant forbids.
   - `manifest.captureMethod` is still written and is still the only trustworthy record of how a session was captured; it is now always `'sck'`, and a value of `'blackhole'` can only appear on sessions recorded before 2026-08-10.
   - Do not re-add a fallback (gotcha #2). The requirement is not "always record something", it is "never silently record nothing" — any candidate must prove it is capturing real audio *before* the meeting starts.
   - Pattern: `services/recorder.js` → `resolveSystemCaptureMethod()`, `sckStartupVerdict()`, `watchSckStartup()`, `sckSilentWarning()`; `services/dependencies.js` → `resolveSystemAudio()`; `utils/audioDevices.js` → `checkSckAvailable()`.

2. **Session directory contract**: Each recording session creates `recordings/{timestamp}_session/` containing `manifest.json`, `system.wav`, and optionally `mic.wav`. The manifest drives all downstream processing.
   - Why: Transcriber and summariser rely on manifest structure
   - Pattern: `services/fileManager.js` → `ensureDirectoryStructure()`

3. **Process registration**: All spawned child processes (sox, whisper) must be registered with `registerProcess()` in `main.js` and cleaned up on app exit.
   - Why: Orphaned sox processes keep recording indefinitely, filling disk
   - Pattern: `main.js` → `registerProcess()`, `cleanupProcesses()`

4. **British English spelling**: The codebase uses British English throughout — `summariser`, `organisation`, `colour`, etc.
   - Why: Consistency across codebase and UI text
   - Pattern: All files

5. **Privacy-first processing**: Transcription is fully local (whisper.cpp/Parakeet — audio never leaves the machine). Summarisation and vault filing go through the user's own authenticated Codex/Claude CLIs (`runLLM`) — never a third-party service the user hasn't set up themselves.
   - Why: Core product promise — meeting audio never leaves the machine; text processing only uses accounts the user controls

6. **Config store defaults**: `electron-store` defaults are defined in `main.js`. Default recording mode is `'dual'`, default labels are `'Remote'`/`'Me'`.
   - Why: Changing defaults affects all new users and existing users without saved preferences

7. **Calendar permission gating**: The macOS Calendar permission prompt fires on first `EKEventStore` access from the `calendar-helper` Swift binary — not on app launch, not from Electron. The suggester must (a) request access on first start, (b) self-disable if denied, (c) not loop helper invocations against a denied state.
   - Why: Without the user-facing permission flow, the helper exits with code 2/3 every poll and the UI never reflects the actual state.
   - Pattern: `services/calendarSources/macOSCalendarSource.js` → `ensurePermission()`; `main.js` IPC `calendar:requestPermission`.

8. **Single dismiss-state source**: Banner dismissals MUST go through `DismissalRegistry`. The meeting detector and calendar suggester both consult the same registry so dismissing the pre-meeting banner suppresses the in-meeting banner for the same occurrence (and vice versa).
   - Why: Two independent dismissal sets would re-fire the banner the moment Zoom opens, defeating the whole point.
   - Pattern: `services/dismissalRegistry.js` → `isDismissed()` / `dismiss({ kind, expiry })`.

9. **Single idempotent stop path**: Every stop trigger — tray menu, `recording:stop` IPC, silence prompt "Stop & save", and the silence grace-timer auto-stop — MUST route through `stopRecording()` in `main.js`. It carries an in-flight guard (`stopInProgress`) so concurrent triggers no-op rather than double-stopping.
   - Why: The silence feature adds *two* new stop triggers; divergent stop paths (the old tray vs. IPC duplication) drift in behaviour and a double-stop can orphan sox/SCK processes.
   - Pattern: `main.js` → `stopRecording()`; callers `handleStopRecording()`, IPC `recording:stop`, IPC `silence:stopNow`, `silenceGraceTimer`.

10. **Silence detection is per-track, never auto-stops on unknown audio**: Each poll classifies every track as **live** (file grew), **unknown** (briefly not grown, `< STALL_TIMEOUT_MS` = 120s), or **ended** (not grown for `>= 120s` — capture is dead). The `SilenceWatcher` judges silence over the **live** tracks only: any relevant track `unknown` pauses the whole poll (a transient stall must not masquerade as a finished meeting); a long-stalled track is **ended** and *excluded* (it no longer poisons the decision — the 2h39m-for-25min incident, session 2026-05-29_20-03-47); when **all** relevant tracks are `ended` (a fully-dead capture) the poll is treated as silence. Every path still routes through the prompt + 60s grace timer — it **never** silently stops. `LevelMonitor` returns level `0` on read failure, indistinguishable from silence, which is why the unknown/ended split (not raw levels) gates the decision.
   - Why: The whole risk surface is accidentally killing a valid recording; the prompt-then-grace design is the safety net for the SCK zero-fill case (gotchas #5). A single global `healthy` boolean conflated transient and permanent stalls and disabled auto-stop for a half-dead capture.
   - Pattern: `services/silenceWatcher.js` → `classifyTrackGrowth()` + `update(levels, { trackHealth })`; per-track growth computed in `main.js` `startLevelMonitor()`. Tested in `services/silenceWatcher.test.js` (`npm test`, plain node).

11. **No recorder reinit mid-recording**: `settings:update` MUST skip `initRecorder()` while a recording is active (`isRecordingActive()`). Swapping the `recorder`/`dualRecorder` references mid-capture orphans the live processes; recorder-affecting settings apply on the next start.
   - Why: The always-wired Save button makes a mid-recording settings save reachable; saving silence settings during a recording must not tear down the live recorder.
   - Pattern: `main.js` IPC `settings:update` → `if (!isRecordingActive()) initRecorder();`.

12. **The handoff directory is the ONLY cross-process channel; the MCP server is read/stage-only**: The standalone MCP server (`mcp/server.js`) and the Electron app communicate *exclusively* through the filesystem handoff at `~/Library/Application Support/CXNotes/handoff/prepared` (computed by `shared/paths.js`, never `app.getPath`). The MCP server only **reads calendars + stages** prepared meetings (atomic tmp+rename); the app only **reads + claims** them (atomic `rename .json → .applied`). The MCP server NEVER drives a recording — there is no live-control bridge. Both sides build the template from the same `services/meetingTemplate.js` and agree on paths via the same `shared/paths.js`, so a prepared meeting and the recording the app starts can never diverge. Never route this state through `electron-store` (a second writer would clobber it).
   - Why: Two processes, one with no Electron context, must agree on a path with zero ambiguity (`name:"cxnotes"` vs `productName:"CXNotes"` makes `app.getPath('userData')` dev-vs-packaged ambiguous — hence the frozen literal). A live-control bridge would couple the two lifecycles; the file handoff keeps them independent (the app can be closed when meetings are prepared).
   - Pattern: `shared/paths.js` → `getPreparedDir()`; `services/preparedMeetingStore.js` (filename suffix `.json`/`.applied`/`.cancelled` is the authoritative state); `mcp/handlers.js`; `main.js` IPC `meeting:confirmRecord` → `claim()`.

13. **The skeleton is a sibling file gated on dual-track; the manifest stays flat**: The rich structured note skeleton is written to `<sessionDir>/meeting-skeleton.md` (the human jots live notes here; the AI summary still lands in `notes.md` — they never collide). Only the flat `{title, participants, agenda}` subset reaches `manifest.json` (invariant #2, summariser unchanged). Skeleton writing is gated on `useDual` — system-only mode returns a flat `.wav` with no session dir, so it is skipped + logged (never written to `undefined`).
   - Why: Widening the manifest with nested keys would fight invariant #2 and the recorder only copies the flat three. A sibling file keeps the rich template without touching the manifest/summariser contract.
   - Pattern: `main.js` → `writeMeetingSkeleton()` inside `startRecordingWithContext()` (after `dualRecorder.start()`); render via `services/meetingTemplate.js` → `renderSkeletonMarkdown()`.

14. **cxmail is the primary calendar source, read-only, with EventKit as automatic fallback**: EventKit only sees events *committed to the Mac Calendar*, so it silently misses meetings that exist only as an unaccepted `.ics` invite or a Zoom link in an email body — the exact meetings the user cares about. `CxmailCalendarSource` closes that gap by reading cxmail's SQLite store (`~/Library/Application Support/com.cxmail.app/cxmail.db`) **read-only**, by spawning `/usr/bin/sqlite3 -readonly -json` (registered via `registerProcess`; never write — a second writer would corrupt cxmail's DB). `FallbackCalendarSource` selects per the `calendarSource` setting: `'auto'` (default) uses cxmail when its DB is present and falls back to EventKit otherwise, so users without cxmail keep the original behaviour for free; `'cxmail'`/`'macos'` force one. cxmail rows carry no attendee list, so eligibility is established by provenance (`source='ics'`, or `source='detected'` with `confidence >= cxmailCalendarMinConfidence`, default 0.7) and the mapped events carry `meetingWorthy:true` so the shared `meetingFilter` skips its ≥2-attendee gate (all-day/declined/denylist still apply). This is a *separate* channel from invariant #12 (which governs the CXNotes-app ↔ CXNotes-MCP pair): cxmail ingestion is one-way, read-only, and CXNotes never writes to or controls cxmail. **Normalisation (2026-07-02, ported from meeting-copilot):** cxmail stores **one row per (invite × mailbox)**, so the source is NOT a per-row mapper — it does fetch → resolve times → **group/dedup → one clean event per meeting**. Dedup keys on `event_uid` (null-UID `detected` rows fall back to `summary|floor(startMs/60000)`), newest `created_at` wins for time/title, attendees union across REQUEST + RSVP-reply rows, `cleanTitle`/`cleanDescription` strip RSVP prefixes + Google `-::~:~::-` boilerplate, conference rooms are excluded, and `resolveEventTime` handles UTC/floating/TZID (DST-correct). The banner/confirm/skeleton flow and the tray "Upcoming on your calendar" menu (see Key Patterns) both consume this deduped shape — the ONE behavioural change is the fingerprint, now per-dedup-group (`cxmail:${uid||summaryKey}:${startISO}`) not per-row; safe because the only fingerprint consumers are in-process (banner ↔ dismissal ↔ confirm/menu claim) — the MCP handoff uses EventKit only.
   - Why: The whole bug was false *negatives* — a real meeting cxmail surfaced that EventKit/CXNotes missed because it was never accepted onto the calendar. The fallback keeps the feature working for every user; read-only protects cxmail's data. Dedup/cleaning fixes false *duplicates* — the same invite firing several banners with `Accepted: …` titles and Meet boilerplate.
   - Pattern: `services/calendarSources/cxmailCalendarSource.js` → `_normalizeRows()`/`_buildEvent()`/`_dedupKey()`/`resolveEventTime()`/`cleanTitle()`/`cleanDescription()`, `fallbackCalendarSource.js`, `index.js` → `createCalendarSource()`; `services/meetingFilter.js` `meetingWorthy` bypass; store keys `calendarSource` / `cxmailCalendarMinConfidence` (`main.js` defaults + `settings:update`). Tested in `services/calendarSources/*.test.js` (`npm test`).

15. **The menu-bar panel is a VIEW, never a second source of truth**: The tray popover (`renderer/menubar-panel.html`) owns no recording state. It reads a snapshot via `panel:getState` and receives pushed updates on `panel:state`; every action it offers routes through the SAME guarded path the tray and settings window already use — `handleStartRecording()`, the single idempotent `stopRecording()` (invariant #9), and `startFromUpcoming()` for a 1-click calendar record (which itself mirrors `meeting:confirmRecord`, invariant #8). It must never call a recorder directly or hold its own copy of the upcoming/marker lists.
    - Why: A second control surface that talks to the recorder directly re-introduces exactly the divergent stop/start paths invariant #9 exists to prevent. As a pure view, the panel cannot disagree with the tray about what is recording.
    - Also: `tray.setContextMenu()` is deliberately NOT used — it swallows the left-click. Left-click toggles the panel, right-click pops up the (still complete) context menu via `tray.popUpContextMenu(trayContextMenu)`. A close is timestamped (`panelClosedAt`) because macOS fires the panel's `blur` BEFORE the tray click, so a naive toggle would close-then-immediately-reopen.
    - Pattern: `main.js` → `createTray()`, `toggleMenubarPanel()`, `buildPanelState()`, `pushPanelState()`, `panelAnchorFor()`; `preload-menubar-panel.js`.

16. **Live markers persist to disk as they are dropped, and reach the summariser through the manifest**: A marker (`⌘⇧M`, the panel, or the tray menu) is written to `<sessionDir>/markers.json` at the moment it is created — not held in memory until stop — so a crash mid-meeting keeps them. At stop the list is flushed again, and `processSession` reads it **from disk** (never from memory) into `manifest.markers`, which `generateSessionNotes` renders into the prompt via `renderMarkersBlock`. Reading from disk is what makes reprocessing an older session pick up its markers too. An empty list renders an empty string, so a marker-free session produces a byte-identical prompt to before the feature.
    - Why: Markers are the user's real-time judgement about what mattered; losing them to a crash or a reprocess would make the feature untrustworthy, and the whole point is that they steer the summary.
    - Gated like the skeleton (invariant #13): system-only mode has no session directory, so `writeMarkers` is a no-op there and the markers live only for the panel's display.
    - Pattern: `services/markers.js` (pure, injected fs); `main.js` → `dropMarker()`, `activeSessionDir()`, `appendMarkersToSkeleton()`; `services/summariser.js` → `generateSessionNotes` markers block. Tested in `services/markers.test.js`.

17. **The vault directory is RESOLVED, never a literal — and "no vault" is a first-class state**: Nothing may hard-code an export target. Every consumer goes through `getVaultDirectory()` in `main.js` (app) or `resolveVaultDirectoryForScript()` in `services/vaultLocator.js` (the non-Electron scripts), both of which can legitimately return **null**. Null means notes are still recorded, transcribed and summarised into the recordings folder — only the vault export is skipped. The store key `vaultDirectory` is deliberately **absent from the `store` defaults**, because `store.has()` is the only thing that separates "never configured" (→ run the one-time detection) from "the user deliberately cleared it" (→ export nowhere, and do NOT re-detect). Detection order is legacy `~/Documents/CX` if it still exists → Obsidian's own registry (`~/Library/Application Support/obsidian/obsidian.json`, open vault first, then most-recently-used, pruning dead entries) → `''`. The legacy path is passed in by the caller as `preferPaths`; `vaultLocator.js` itself knows no personal paths, which is the whole point.
    - Why: the export target was `path.join(app.getPath('documents'), 'CX')` — correct for exactly one person and silently wrong for everyone else, creating a stray `~/Documents/CX` folder on any other machine. Reading Obsidian's registry means a new user's vault is found without them configuring anything, and the legacy preference means an existing install never jumps vaults on upgrade.
    - The empty string is persisted after a *failed* detection too, so the scan doesn't repeat on every call; the settings window's **Detect** button is the way back for someone who installs Obsidian after CXNotes.
    - Pattern: `services/vaultLocator.js` (pure, injectable `fsImpl`, home directory a parameter); `main.js` → `getVaultDirectory()`, `LEGACY_VAULT_DIRECTORY`, IPC `system:chooseVaultDir` / `system:detectVaultDir`, `settings:get`/`settings:update` key `vaultDirectory`; `summarise-only.js`; `scripts/file-root-notes.js` (`--vault` still overrides). Tested in `services/vaultLocator.test.js`.

18. **Window glass is NATIVE + tint, and the two halves must agree**: Every window carries a real `NSVisualEffectView`, requested with Electron's `vibrancy` option (`main.js` `GLASS.popover` for floating surfaces, `GLASS.window` for full windows, both `visualEffectState: 'active'`). `backdrop-filter` **cannot** do this job — it blurs an element's backdrop *root*, which for anything inside the page is the page, so on a transparent window it blurs a transparent nothing. The panel carried `backdrop-filter: blur(30px)` for exactly this purpose and it was always a no-op; the surfaces around it were near-opaque to hide the fact that a translucent pane showed the desktop through *sharp*. Three things are required and any one missing makes the other two look broken: (a) the window asks for a material, (b) the document paints **no** background — `body`/`html`/`.container`/`.pop` are all `transparent`, (c) each pane paints its own tint via `rgb(var(--surface-x) / var(--alpha-y))`. The three alphas come from ONE dial (`windowTransparency`, default 0.38) through `services/glass.js` `transparencyToAlphas()`, which guarantees `chrome <= pane <= card` at every position, and are stamped onto `<html>` as an **inline style** by `applyGlass()` — inline because it beats every selector, so the opaque `:root` fallbacks each renderer declares can only ever serve the pre-push first paint. **No pane may paint on top of another pane's background**: a shared background under everything means each alpha composites over *that* instead of over the material, so turning the dial moves a pane toward the shared colour rather than toward the desktop, and reads as the setting doing nothing. Which surfaces are alpha-aware is a decision: `--bg-input`/`--bg-elevated` stay **opaque** because they are what you have to read and type into, and native `<select>` menus render over the desktop.
   - Why: the whole point is real depth against the user's own wallpaper; a fake blur produces a flat panel with a legible desktop behind it, and stacked panes produce a transparency setting that visibly does nothing.
   - Density is per-window-class, not global: a full window you sit and work in puts its CONTENT on `--alpha-pane` and its chrome column on the thin `--alpha-chrome` (chrome reads lighter by being thinner). A popover inverts that — its field takes the thin alpha and its bars take `--alpha-pane`, because two thin bars framing a small floating surface dissolve into the wallpaper and the popover loses its edges.
   - Pattern: `services/glass.js` (pure, Electron-free); `main.js` → `GLASS`, `currentTransparency()`, `applyGlass()`, `attachGlass()`, `broadcastGlass()`, IPC `glass:preview` (live drag, persists nothing) + `settings:update` key `windowTransparency`; `renderer/styles.css` + the five renderer `:root` blocks. Tested in `services/glass.test.js`.

19. **The summarisation provider is RESOLVED from one registry, never hard-coded — and `auto` must stay bit-for-bit the old behaviour**: `services/llmProviders.js` (pure, Electron-free) is the single definition of what a provider is (`PROVIDERS`), the order `auto` tries them in (`AUTO_ORDER` = Codex → Claude → Ollama), and how a stored preference becomes an attempt list (`resolveProviderOrder`). Nothing else may name a provider: the renderer builds its `<select>` from what main ships in `settings:get`, `runLLM` iterates the resolved order, and `AUTO_ORDER` is asserted to cover every id so a provider added to the registry can never be silently unreachable. **`auto` is the default and reproduces the pre-setting Codex→Claude order exactly** — an existing install must not change provider on upgrade, which is why that specific ordering has its own test. A named preference goes FIRST with the others still behind it as fallback; **`llmProviderStrict` is the only thing that removes the fallback**, and it exists solely so someone who deliberately picks the local provider cannot have a transcript escalate to a cloud CLI behind their back (invariant #5). An unrecognised stored value degrades to `auto` on BOTH read and write, so a hand-edited config can never stop summarisation.
   - Why: the order used to be two hard-coded `if` blocks, so a Claude-only user silently paid a failed Codex attempt on every meeting, and there was no way to express a preference at all. Ollama is in the registry because both CLIs are paid subscriptions — it is the only "no subscription at all" path, and the only one where the transcript never leaves the machine.
   - **Every LLM entry point threads the same options**, or the app disagrees with itself about which provider it uses: `generateNotes`/`generateSessionNotes` take a trailing `llmOpts`, `main.js` `llmOptions()` reads the store fresh per call (so a change applies to the next summary with no restart), `filingRunLLM` closes them over for `noteFiler`'s injected `runLLM(prompt)`, and the non-Electron scripts get them from `readStoredLlmOptions()`, which reads electron-store's `config.json` reusing `vaultLocator.STORE_DIR_NAMES` so the two cannot drift.
   - Models are pinned per provider and user-overridable (blank = pinned). A blank override is stored as **absent**, so "cleared" and "never set" are one state. Making models configurable widened gotcha #12 — see the model-refusal patterns there.
   - Pattern: `services/llmProviders.js`; `services/summariser.js` → `PROVIDER_SPECS`, `runProvider()`, `runLLM()`, `providerAvailability()`; `main.js` → `llmOptions()`, `filingRunLLM()`, `describeProviders()`, store keys `llmProvider`/`llmProviderStrict`/`llmModels`; `renderer/app.js` → `renderLlmProviders()`, `renderLlmProviderStatus()`. Tested in `services/llmProviders.test.js`.

20. **External binaries are RESOLVED to an absolute path, never invoked by bare name**: no `which`, and no `spawn('sox')`. Everything the app shells out to — `sox`, `codex`, `claude`, `ollama` — goes through `utils/binaries.js` `resolveBinary()`, which searches `$PATH` first (so a developer pointing PATH at a custom build still gets it) and then the places these tools actually live: Homebrew, `/usr/local/bin`, MacPorts, `~/.local/bin`, and every `~/.nvm/versions/node/*/bin`. A model/binary the app *ships with* is found via `process.resourcesPath`; a large asset it cannot ship (the ~141 MB whisper model) lives in `~/Library/Application Support/CXNotes/models`, which is the only location reachable from BOTH a dev run and a packaged app.
   - Why: a macOS app launched from Finder/Dock/Spotlight inherits launchd's environment, and `launchctl getenv PATH` is unset, so it gets `/usr/bin:/bin:/usr/sbin:/sbin` — no Homebrew, no npm-global. Every PATH-dependent lookup fails, which made a packaged CXNotes report sox and all three AI providers missing on machines where they were installed.
   - **The trap is that this cannot be reproduced by the person who built the app**: `open -a CXNotes` from a terminal passes the calling shell's environment through, and that is exactly how the ship command launches it. Testing a packaged app by launching it from a terminal proves nothing about what a user gets. Reproduce with `env -i PATH=/usr/bin:/bin:/usr/sbin:/sbin HOME="$HOME" /Applications/CXNotes.app/Contents/MacOS/CXNotes` (gotcha #14).
   - Repo-relative candidates (`./whisper.cpp/…`, `path.join(__dirname, '../models/…')`) are dev-only by construction: cwd is `/` for a Dock-launched app and `__dirname` points inside the bundle. Keep them last and never rely on them.
   - Pattern: `utils/binaries.js` (pure, injectable `fsImpl`/`env`/`home`); `services/recorder.js` → `soxBin()`; `main.js` → `resolveBinaryCached` in both dependency checks; `services/summariser.js` → `isProviderAvailable()`, `runProvider()`; `services/transcriber.js` → `bundledResourcesDir()`, `getModelsDir()`. Tested in `utils/binaries.test.js`.

21. **Quitting DRAINS its children — SIGTERM, wait, then SIGKILL**: `before-quit` may not simply signal and return. It is synchronous, so the app exits the instant it returns, and anything slower than that is orphaned with nothing left to reap it (invariant #3). Teardown goes through `services/processRegistry.js`: `shutdown()` sends SIGTERM to every registered child, polls for a grace period (2s), then SIGKILLs whatever ignored it. The quit itself is deferred with `event.preventDefault()` plus a `shutdownStarted` re-entry guard, and `shutdown()` **always resolves** — a cleanup that can hang is worse than one that kills a moment early, because an unquittable menu-bar app has to be force-killed, which orphans everything anyway.
    - The grace period is not politeness: a child killed outright never finishes writing. The ScreenCaptureKit helper finalises its WAV header on SIGTERM, and skipping that leaves a file every player reads as zero-length.
    - Scope: the recorders kill their own sox/SCK processes synchronously first (`recorder.cleanup()` / `dualRecorder.cleanup()`, both SIGKILL), so the registry covers the *helpers* — `sqlite3` against cxmail's store, `calendar-helper`, the `open` shell-out, and audio post-processing.
    - **`proc.killed` is not "the process died".** In Node it means a signal was successfully SENT. A child that ignores SIGTERM still reports `killed === true`, so trusting it makes the escalation unreachable — which is exactly what the first implementation did. `ProcessRegistry.hasExited()` reads `exitCode`/`signalCode` and deliberately ignores `killed`. Every fake agreed with the bug; only a test against a real `sh -c 'trap "" TERM; sleep 30'` caught it, which is why that test exists.
    - Pattern: `services/processRegistry.js` (pure, injectable timers); `main.js` → `childProcesses`, `registerProcess()`, `app.on('before-quit')`. Tested in `services/processRegistry.test.js`.

22. **A system-capture restart NEVER touches the mic, always writes a NEW file, and stitches with a padded gap**: when the system capture dies (the helper exits non-zero) or is proven to be delivering nothing (`SignalWatcher`), it is started again **in place** — same ScreenCaptureKit helper, same method. This is not a fallback and does not violate invariant #1; nothing switches. Three rules make it safe:
    - **The microphone is not involved.** `restartSystemCapture()` signals only `this.systemProcess`; it does not reference `micProcess` or `micFile` at all, so `mic.wav` grows unbroken straight through. That is what makes a restart recoverable rather than destructive — the worst case is a gap in one track, never a gap in both. Verified against a real `kill -9` mid-session: the mic file grew at every 500 ms sample across the kill.
    - **A restart must write to a new path.** The helper truncates whatever file it is given, so reusing `system.wav` would delete everything recorded so far. Parts are `system.wav`, `system.part2.wav`, `system.part3.wav`, and **parts are never deleted** — they are the only copy of the audio, and if a stitch is ever wrong the raw material to redo it by hand is still on disk.
    - **The gap is padded, and the pad is mandatory.** `transcriptMerger` orders the merged transcript by each file's own internal offsets, so a system track shorter than the wall-clock time it spans misattributes every word after the gap and the speakers interleave wrongly for the rest of the meeting. `planStitch()` (pure) derives each part's true audio start **backwards from when it stopped** (`audioStart = stoppedAt - duration`) rather than forwards from its spawn time, which self-corrects for ScreenCaptureKit's 1.7-3s startup latency; a spawn-time calculation cannot. Pads are interior, so `trimSilence` (leading/trailing only) cannot eat them.
    - **The permission to restart must be re-checked AFTER the old helper is drained, not just before.** Killing it takes up to `RESTART_STOP_GRACE_MS`, and a stop landing inside that window has already captured `systemProcess` into its own kill list and moved on — so a replacement spawned afterwards belongs to nobody and records forever with nothing left to reap it (gotcha #4). `_canOwnNewCapture()` exists as a separate predicate precisely because `canRestartSystemCapture()` cannot be re-run mid-restart: `_restartingSystem` is true by then and it would refuse every time.
    - Failure is survivable by construction: `system.wav` IS part one, so a failed stitch leaves exactly what the session would have produced before any of this existed. `_replaceSystemFileWith()` undoes its first rename if the second fails, because a session with NO `system.wav` reports the track missing — strictly worse than keeping the pre-restart audio. And when only ONE part holds audio, the survivor is **promoted** to `system.wav`: if part one never produced a byte, leaving it in place would discard the recording in exactly the case where the recovery worked.
    - Guardrails: at most `SYSTEM_RESTART_MAX` (2) per session, `SYSTEM_RESTART_MIN_INTERVAL_MS` (30s) apart, never while stopping. A restart re-arms the `SignalWatcher`, clears the track's `trackGrowth` entry and re-points the `LevelMonitor` at the new part — all three, or: the replacement is judged on the dead capture's silence and burns the budget in two polls; and its file starts at a 44-byte header, so `size > lastSize` is false every poll and a healthy capture reads as `stalled` then `ended`.
    - Single-track mode has no restart path and no second track, so a stream death there ENDS the recording (`isRecording` goes false and `stopRecording()` skips as "nothing to stop"). The audio is still on disk and still listed with a Process button, so the recorder warns the user rather than letting the recording vanish mid-meeting.
    - Pattern: `services/recorder.js` → `restartSystemCapture()`, `_spawnSystemCapture()`, `canRestartSystemCapture()`, `stitchSystemParts()`, `planStitch()`, `resolveFinalTrackStatus()`; `services/levelMonitor.js` → `retargetTrack()`; `main.js` → `handleDeadSystemSignal()`, `dualRecorder.onSystemPartChange`. Tested in `services/recorder.test.js`.

23. **The capture is PROVEN by playing a known sound into it — and a probe only decides when the capture is quiet**: at recording start, and before acting on any `SignalWatcher` verdict, CXNotes plays a two-tone signature through the machine's own output and looks for exactly that signature in the captured samples. Everything else in the system waits to SEE whether audio turns up and reasons about the silence; this makes us the thing that is playing, which collapses the one genuinely ambiguous reading — "the capture is dead" versus "nothing is playing yet" — into a fact.
    - Why: invariant #1 has always demanded a capture path "prove it is capturing real audio". Measuring samples (2026-08-14) got half way: it can tell silence from audio, but not a dead capture from a quiet room, so a verdict needed 45 s of mic corroboration that `SignalWatcher`'s own doc comment calls a deliberately weak bet. A probe needs no corroboration and takes about three seconds.
    - **A probe result is only consulted when the region is silent.** If the captured region holds REAL AUDIO the capture has already proven itself and the probe is not asked — which is what makes two awkward measurements harmless: a 200-trial-per-level Monte Carlo found false positives under broadband noise AND true positives collapsing under masking. Both live entirely in the loud regime, which the audio path answers first. The quiet regime, where the probe actually decides, measured zero false positives in 200 trials and 50/50 true positives. Never promote a probe result to a verdict without that gate.
    - **The three verdicts are `alive` / `dead` / `inconclusive`, and `inconclusive` is not rounded.** A probe we could not PLAY (missing `afplay`, spawn failure, timeout) proves nothing about the capture, and reporting it as failure would blame the capture for our own silence — the false alarm that teaches people to click past every later warning. Same for a faint signal that is neither audio nor our signature.
    - **This covers BOTH recording modes**, unlike the passive watcher. Single-track gets no `SignalWatcher` verdict because there is no second track to corroborate with (gotcha #16) — but there is nothing to corroborate when we are the sound source, so start-time verification closes that gap. It does not close the mid-meeting half: system-only still has no restart path.
    - **A dead verdict at start is re-probed once before it interrupts anyone.** Waiting for the capture file to grow past its header proves the stream STARTED, not that it is delivering audio yet. Measured, the gap is comfortable (frames at ~605 ms, 5 runs of 5 clean), but that was an idle machine, and a wrong "your audio is dead" dialog in the first seconds of a real meeting would discredit every true warning after it.
    - Amplitude is a POLITENESS decision, not a detection one. ScreenCaptureKit taps ahead of the master volume, so the captured level tracks the amplitude in the file and is independent of the user's output volume — measured identical with output **muted** and at **volume 0**. Nobody working muted can be handed a false verdict, and the probe played during a live meeting is quieter than the one at start because the far side of a call can hear it. Do NOT mute the user's output to hide a probe, however well it would work.
    - Losing the probe must never leave the app worse off than before it existed: with no usable verdict, `confirmDeadSystemSignal` falls through to exactly the previous inferred behaviour (quiet first verdict, loud on the second).
    - Pattern: `services/captureProbe.js` (pure — synthesis + Goertzel detection, with the measurements behind every constant in its header); `services/probeRunner.js` (`verifyCapture()`, `playSignature()`, `readWavSamplesFrom()`); `main.js` → `verifyCaptureAtStart()`, `probeSystemCapture()`, `waitForCaptureStream()`, `activeSystemCaptureFile()`, `confirmDeadSystemSignal()`, `showDeadCaptureDialog()`. Tested in `services/captureProbe.test.js` + `services/probeRunner.test.js`. Gotcha #17.

24. **Frame capture is scoped to ONE window, never a display and never an application**: `SourceResolver` (`native/sck-slide-capture/`) resolves the meeting audio's owner to exactly one `SCWindow`, and `SCContentFilter(desktopIndependentWindow:)` is the only filter shape the slide helper ever builds. Every other branch throws `ResolutionFailure` and captures nothing.
   - Why: a person reads mail, checks Slack and looks at their bank during a meeting — that is the normal case, not the edge case. "Record the screen and crop" leaves the user's other windows in the frames on disk; window-scoped capture returns the target window's own content wherever it sits in the stacking order, so what is in front of it was never in the frame at all. The guarantee is structural, not a policy someone has to remember.
   - **Refusal is the common case and it is quiet.** Zoom running in the background with no meeting window, or a browser holding the audio with no window title that names a meeting, both capture nothing and record the reason in the manifest. A browser TAB is invisible to the OS, so two candidate windows is a refusal too — never a guess.
   - **The one widening is the share case, and it narrows again on its own.** When the user is sharing, their slides are in Keynote or a browser, not in the meeting window (Zoom does not render your own share back to you). Capture follows to the window they are presenting FROM, latched at share-start, so alt-tabbing to Slack mid-share does not repoint the camera. What is captured is what the room can already see.
   - **Slides may never take audio down.** The helper is a separate process from `sck-audio-capture` precisely so invariant #1's no-fallback guarantee is never at risk; `SlideCaptureSession.start` reports instead of throwing, and the recorder starts slides last.

25. **Vault filenames are `<CATEGORY> <Who|Topic> <MM.DD.YY>.md`, ≤40 chars**: category derives from the destination FOLDER; a folder with no code (the `Meetings/` catch-all) may EARN one from content (`categoryForContent`) and otherwise gets **no prefix** — there is no default code; there was one until 2026-09-08 and it landed on calls it had nothing to do with. The folder codes, the content codes and the user's own names are not in the code: they come from the vault profile (`services/vaultProfile.js`, the `vaultProfile` setting), and an empty profile means no category at all. The user is never named, the date is last and never truncated, and the compression ladder ends in *truncating the topic* — the literal `Meeting` is only for an empty middle, never a stand-in for a topic that did not fit. A note that moves folders must be re-stamped (`restampCategoryForDestination`) or the code lies. `summarise-only.js` and `scripts/file-root-notes.js` read the same profile through `readStoredProfile()`, so a script names a note the way the app would.
   - Numbered 25 on 2026-09-25: until then this rule lived only in `CLAUDE.md`'s own invariant list (as its #6), which used a different numbering from this file.
   - Pattern: `services/summariser.js` → `buildObsidianFilename()`, `truncateMiddle`, `categoryForContent()`, `categoryForDestination()`, `restampCategoryForDestination()`. History: `docs/learnings.md` 2026-09-08.

26. **Call audio is ADDITIVE: a session without a call is left exactly as ScreenCaptureKit wrote it.** iPhone-handoff and FaceTime calls are played by the system daemon `avconferenced`, which ScreenCaptureKit cannot hear (gotcha #24). `native/call-audio-tap` records it, under three rules that together keep every other recording structurally untouched:
   - **Its own process.** Never inside `sck-audio-capture`, for the reason slides are not (#24): a crash, a hung permission prompt or a Core Audio error costs call audio and nothing else. The recorder starts it last, `CallCaptureSession.start` reports rather than throws, and `stop()` always resolves within `CALL_STOP_GRACE_MS`. It is registered for the quit drain (#3/#21).
   - **Lazy.** While no call plays, the helper only reads `kAudioProcessPropertyIsRunningOutput` on the daemon's process object every 250 ms. It builds a tap (per-process, `.unmuted`, private, tap-only aggregate) only while that reads 1, and tears it down when it drops. Measured in the T206 spike: the daemon stayed at 0 through a whole Zoom call (mic + camera) and a Meet call, and read 1 for exactly the 16 s of a FaceTime voicemail call. So a normal meeting gets no tap, no device and no file. Every session still records `manifest.callAudio.segments`, so a real meeting that ever trips the tap is visible rather than assumed impossible.
   - **Mixed only when there is call audio.** `planCallMix` returns `[]` for no segments, a silent segment, or an unusable clock, and `[]` means nothing is read, written or renamed — pinned by tests through the real `stop()` path. When there IS call audio, `system.wav` is stepped aside to `system.sck.wav`, the mix lands at `system.wav`, the renames undo each other on failure, and `call.N.wav` is never deleted. `-D` (no dither) keeps every ScreenCaptureKit sample outside the call bit-identical.
   - **Placed on the MIC's clock.** The transcript merge treats sample 0 of both tracks as the same instant, and on a phone call what must line up is the other side's turns against yours. The mic's first sample is derived backwards from the stop request (`_stopRequestedAt - duration`), the move `planStitch` makes for restarts.
   - Off by default (`callCaptureEnabled`). Switching it on runs `call-audio-tap --request-access`, because the first-ever tap blocks about a minute on the System Audio Recording prompt and that must not happen mid-call. The grant needs `NSAudioCaptureUsageDescription` in the app's Info.plist; without it macOS delivers zeros with no error and no prompt, which the helper's `silent-tap` event turns into a warning — one that can only fire during a call.
   - Pattern: `native/call-audio-tap/` (`CallTap`, `CallWatcher`, `WavWriter`); `services/callCapture.js` (`planCallMix`, `mixCallAudio`, `effectiveSampleRate`, `CallCaptureSession`); `services/recorder.js` → `_finishCallAudio()`; `main.js` → `createCallCapture()`, `requestCallAudioAccess()`. Tested in `services/callCapture.test.js` and the call-audio tests at the end of `services/recorder.test.js`.

## Key Patterns

### IPC Communication
- Main ↔ Renderer communication via `ipcMain.handle()` / `ipcRenderer.invoke()`
- Preload script exposes safe API through `contextBridge.exposeInMainWorld()`
- All IPC channels defined in `preload.js`

### Recording Flow
1. User clicks "Start Recording" in menu bar
2. Preflight checks run (sox, system-audio capture — SCK only — mic, LLM provider)
3. `DualTrackRecorder` starts two tracks: system via the SCK helper + mic via sox
4. On stop: both wav files saved to session directory
5. `transcribeSession()` runs whisper.cpp on each track → CSV output
6. `transcriptMerger.js` merges per-track CSVs with speaker labels
7. `generateSessionNotes()` sends merged transcript through `runLLM` (Codex CLI → Claude CLI fallback)
8. Markdown notes saved alongside recordings, then auto-filed into the vault via `fileAndExportNotes()` (see Vault Auto-Filing)

### Audio Device Detection
- `system_profiler SPAudioDataType` parsed for device enumeration
- Device names at 8-space indent, properties at 10-space indent
- `listInputDevices()` returns all available input devices

### Calendar-Driven Templated Meetings (+ standalone MCP)
Two processes that meet only through the filesystem handoff (invariant #12):

1. **Prepare (optional, ahead of time)** — a background process / Claude routine calls the MCP server's `prepare_meeting({fingerprint|eventId})`. The server reuses the EventKit `calendar-helper`, builds the template via `meetingTemplate.js`, and stages a record to `handoff/prepared/cal_<id>.json` (atomic). Works with the app closed. No ports — stdio only.
2. **Detect** — the app's `MeetingDetector`/`CalendarSuggester` fires on a call. If a `calendarEvent` is present AND `calendarAutoTemplateEnabled` is on, `decideBannerMode()` returns `'confirm'`; else today's `'suggest'` flow is preserved.
3. **1-click confirm** — the banner shows a single **Record** button → IPC `meeting:confirmRecord` → `buildMeetingContext(event)` → `recordDismissal()` (same `DismissalRegistry`, invariant #8) → `preparedMeetingStore.claim(fp)` (best-effort; works with no prepared file) → `startRecordingWithContext(richCtx)`.
4. **Skeleton** — after `dualRecorder.start()`, `writeMeetingSkeleton()` writes `meeting-skeleton.md` (invariant #13). The flat `{title,participants,agenda}` still flows to the manifest; the summariser is unchanged.

**Tray "Upcoming on your calendar" menu (2026-07-02)** — the menu-bar analog of the confirm banner. The suggester's single 60s poll is widened to a 12h horizon (`MENU_WINDOW_MINUTES=720`; banner timing unchanged because the fire loop re-gates on `msUntilStart <= leadMs`), then derives a filtered/deduped/≤5 list and fires `onUpcoming(list)`. `main.js` caches it in `cachedUpcomingMeetings` and `updateTrayMenu()` renders a section (header + one item per meeting, `⏱ 4:00 PM · <title>`, `🟢 … (soon)` within 10 min) when idle. Clicking → `startFromUpcoming(ev)`, which mirrors `meeting:confirmRecord` exactly (`buildMeetingContext` → `recordDismissal({fingerprint, calendarEvent})` on the same registry → best-effort `preparedMeetingStore.claim` → `startRecordingWithContext`). The cache is cleared at recording start and when suggestions are toggled off; it repopulates on the next poll after a stop.

Permission caveat (gotcha #8): a headless MCP-spawned helper may be keyed to a different code signature than the granted one. `shared/paths.js` prefers the installed app's signed helper; `npm run mcp:check` drives the grant + reports the fix.

### Menu-Bar Panel + Live Markers (2026-07-30)

**The panel.** Left-clicking the tray icon opens a frameless, transparent popover anchored under it (right-click still opens the full context menu). Two states in one window:
- **Idle** — a big Start button, the next calendar meeting as an accent card with a 1-click **Record this meeting**, the rest of the day as compact rows, and the most recent exported notes with the vault folder each was filed into (read from `manifest.processing.vaultFiling`, so an Inbox escalation shows an amber "needs a home" dot).
- **Recording** — elapsed timer, one live level-history strip per track (40 bars ≈ 10s of the *real* RMS data the silence watcher consumes), a per-track health chip, the marker input + list, and Stop & process.

Positioning is defensive: `tray.getBounds()` is not trustworthy (an auto-hidden menu bar returns an off-screen origin — observed x = -9294 on a single-display Mac), so the bounds are validated against `screen.getAllDisplays()` and anything not landing on a real screen falls back to the top-right of the active display's work area. Both axes clamp into the work area. The renderer measures its own content and asks main to fit the window (`panel:resize`, clamped 200–760px).

**Track health in the menu bar.** `computeTrackHealth` now runs every poll regardless of whether the silence watcher is armed, and the map is cached in `latestTrackHealth` for the panel. A track that stops growing for 120s renders as a red `stalled` chip **while the meeting is still running** — the SCK zero-fill failure (gotchas #5/#6) used to be discoverable only after the fact.

**Markers.** `⌘⇧M` (registered only for the duration of a recording, so the combination is free otherwise), the panel's input, or the tray's "Drop Marker" item timestamps the current moment. See invariant #16 for the persistence contract. Markers also get appended to `meeting-skeleton.md` under a `## Flagged Moments` heading (idempotent — a reprocess replaces the block rather than stacking).

**Tray title.** Idle shows the bare glyph; recording shows `⏺ 24:36` followed by the existing per-track level blocks, so elapsed time is readable without opening anything while the level bars still expose a dead track in place.

### Opening Notes — Obsidian Where It Can, a Plain Editor Where It Can't (2026-07-30)

Every "open this file" path (`files:open` from the settings window, `panel:openPath` from the menu-bar panel) routes through `openArtefact()`:

| File | Opens with | Why |
|------|-----------|-----|
| Markdown **inside** the vault | Obsidian, via `obsidian://open?path=<abs>` | The URI works regardless of which app owns `.md` system-wide, so it survives the user changing their default handler |
| Markdown **outside** the vault (a session's raw `notes.md`, a merged transcript) | `plainTextEditor` store key, default `TextEdit`, via `open -a` | Obsidian can only open files in a vault; handed a loose note it offers to create a vault inside the recordings folder |
| Anything else (`.wav`, `.csv`) | System default (`shell.openPath`), unchanged | — |

`isInsideVault()` resolves symlinks on both sides before comparing (the vault symlinks a couple of folders) and tests containment on a **path-segment boundary** — a bare `startsWith` also matches a sibling like `~/Documents/CX-archive`. Every fallback degrades to `shell.openPath` rather than failing, so no branch is a dead end.

### Vault Auto-Filing of Exported Notes (2026-07-20)

Every note export routes through `main.js` `fileAndExportNotes()` instead of calling `exportNotesToVault()` directly (5 call sites: dual auto-process, single-track, and the three reprocess IPCs). The routing brain is `services/noteFiler.js` — **pure, Electron-free, injectable fs** — and its tier flow:

1. **Deterministic** — `scoreDestinations()` scores every candidate destination (keyword-in-title +3, keyword in participants/agenda +1.5, rule person in participants +2, participant-token overlap with existing destination filenames +1 each **capped at +2** — attendee names recur across folders, so overlap is a scored signal, never a binary router). Routes without the LLM only at score ≥ 4 AND margin ≥ 2 over the runner-up.
2. **LLM fallback** — `runLLM` (Codex CLI primary → Claude CLI, exported from `summariser.js`) picks from the top-5 scored candidates + `"none"`, raced against a 90s timeout, strict single-JSON-object contract parsed defensively (`parseFilingResponse` → null on anything off). Valid id at confidence ≥ 0.6 files there; `"none"` at ≥ 0.6 → catch-all.
3. **Escalation** — LLM unavailable/timeout/garbage/low-confidence with SOME scoring evidence → note files to `Inbox/` + a frameless triage pop-up (silence-prompt recipe: `preload-filing-prompt.js`, `renderer/filing-prompt.html`, IPC `filing:getContext`/`filing:choose`/`filing:dismiss`, 4-min auto-hide; a newer escalation replaces an open prompt — the earlier note is already safe in Inbox). Zero evidence → top-level `Meetings/` catch-all with **no** pop-up (a brand-new person/product must not spam escalations).

Candidate destinations = the `vaultFilingRules` store key (there are no built-in rules; `DEFAULT_FILING_RULES` is empty, merged by `mergeFilingRules`) **plus auto-discovery** of `<parent>/<name>/<subdir>` for each of the vault profile's `discoveryGroups` — onboarding a new client is just creating the folder.

Safety contract: `classifyNote()` never throws (null → caller does the legacy flat export); `fileAndExportNotes()` wraps everything so ANY failure degrades to the flat root export — notes are never lost to filing. `options.existingPath` (reprocess) and `vaultAutoFilingEnabled: false` skip classification entirely. Filed exports get a collision suffix (`Name 2.md`) via `resolveCollision`; the legacy flat export keeps stable-name overwrite semantics. Dual-track sessions record the decision in `manifest.processing.vaultFiling` `{method: deterministic|llm|catch-all|inbox|manual, destination, confidence, reason, decidedAt}` — a sibling of `obsidianExport`, which stays a plain string. One-time root sweep: `scripts/file-root-notes.js` (`--dry-run`).
