- 2026-08-20: **Three findings from building slide capture, each of which invalidated the design that preceded it.** (1) **ScreenCaptureKit is change-driven, not clock-driven.** The first stability test — "the same perceptual hash N frames running" — produced ZERO keyframes over 18s against a plainly-visible static window, because a slide holding still delivers no frames at all. Inverted to a debounce (hold the newest frame; treat the ABSENCE of a newer one as settled), which also turns out to be what separates slides from talking heads with no face detection anywhere. Gotcha #20, which also covers the two traps behind it: SCK interleaves `idle`/`blank` frames that encode as grey rectangles unless you check `status == .complete`, and a `CVPixelBuffer` dies with its callback while a debounced decision to keep it happens later — so the hasher renders a detached `CGImage` and carries that. (2) **The privacy question is a SCOPE question, not a cropping one.** `desktopIndependentWindow` captures a window's own content through whatever is in front of it, so scoping to one window means other apps were never in the frame — verified visually. The corollary is that Zoom does not render your own screen-share back to you, so "capture the meeting window" cannot capture your own slides; that case has to follow the window you are presenting FROM, latched at share-start. (3) **`.fast` Vision OCR is unusable for names** — it reduced clean 12pt text to `Untitl<?> 2 | He vetica` in situ, while `.accurate` read the same window perfectly. It runs every few seconds on its own queue, so the cost is irrelevant and a misread name is not. Related: interpretation of that text lives in JS, not Swift, because that is where the meeting roster is and where heuristics can be tested — on the real OCR noise, 16 garbage lines yielded 0 false names. - 2026-08-17: **Stop inferring that the capture works — prove it.** The Aug-14 work made the app able to tell silence from audio, but a *passive* observer still cannot tell **"the capture is dead"** from **"nothing is playing yet"**, and `SignalWatcher`'s own comment concedes that its mic corroboration is a deliberately loose bet costing 45 s and a restart when wrong. The fix is to stop observing and start participating: CXNotes now plays a known two-tone signature through the machine's own output and looks for exactly it in the captured samples. Once we are the thing making the sound the ambiguity is gone — a missing signature is proof of failure. **Every constant was measured before a line was written**, because gotcha #15's lesson is that the filter shape must be measured, not reasoned about. `afplay` reads **0.999542** through the shipped `excluding` filter and **0.000000** through the per-app `including` one (reproducing #15 exactly, and the reason a probe would have been silently useless six months ago). Two findings then shaped the whole design. **Captured level tracks the amplitude in the FILE, not the system volume** (0.0995 @ vol 50, 0.0999 @ 100, 0.0965 @ 25) because SCK taps ahead of the master volume — and the signature comes back *identical* with output **muted** or at **volume 0**. So detectability and audibility are separate dials: nobody working muted can be handed a false "your capture is dead", and amplitude is chosen purely on politeness (quieter again for probes that play during a live meeting; deliberately NOT muting the user's output to hide one). **The load-bearing design rule came out of a Monte Carlo, not intuition**: 200 trials per noise level found false positives under broadband noise and true positives collapsing to 1/50 under masking. Both are physics, and both are harmless *only* because `verifyCapture` checks for real audio FIRST — audio in the file already proves the capture works, so the probe is never consulted in the loud regime where it is unreliable. In the quiet regime where it does decide: zero false positives in 200 trials, 50/50 true positives. The ratio floor is **40**, set from that distribution rather than from an observation — an earlier 12, which looked safe against a single hardware reading of 9.4, admitted 1.5% false positives, because taking the max ratio across every window is an extreme-value statistic that climbs as the search widens. **What it buys**: all four losses on record were dead from the first second and found after the meeting, if at all; they are now caught in ~3 s. It runs in **both** modes, narrowing gotcha #16's coverage gap — single-track has no passive verdict because there is nothing to corroborate with, and a probe needs no corroboration. Mid-meeting, a `SignalWatcher` verdict became a *suspicion* the probe confirms: a cleared one now costs one quiet tone instead of a restart plus a permanent amber warning (false alarms are what teach people to ignore the real one), and a confirmed one warns immediately instead of waiting out a second five-minute window, because proof needs no probation. Losing the probe falls back to exactly the old behaviour. A dead verdict at start is **re-probed once** first: waiting for the file to grow past its header proves the stream *started*, not that it is delivering audio, and a wrong dialog in the first seconds of a real meeting would discredit every true warning after it. **Verification was the interesting part.** The unit tests caught a temporal-dead-zone bug where a synchronous spawn failure hit `clearTimeout(timer)` before `const timer` initialised — so the one path that had to degrade gracefully was the one path that crashed. The end-to-end test needed no mock for the failure case: the per-app `including` filter *genuinely* records zeros on this machine, so **the bug itself is the fixture**. And the integration run against the real `DualTrackRecorder` printed the whole argument for the feature in one line — the old growth-based check logging *"SCK is producing audio — staying on ScreenCaptureKit"* over a capture that was 100% zeros, three seconds before the probe called it dead. Tests **599 → 653**. New invariant #23, gotcha #17.
- 2026-08-14: **Never silently record nothing** — the invariant #1 clause that was written down but never implemented. The installed Aug-7 binary measured `0.000000` alongside it, so this was never a regression in newer code. Total silence across the *entire* duration fits the evidence far better than a stale app list ever did. The bitter part: **the per-app filter was introduced as the fix for gotcha #5**, on the theory that it bypassed the ARK/ACE hijack — and gotcha #5's own text already conceded that ARK being *loaded* "looks necessary but is NOT sufficient", since the one incident actually resolved was resolved by `sudo killall coreaudiod`. 'complete' : 'empty'` **overwrote** a mid-flight `'silent'` verdict; and `processSession` computed `allSilence` and did nothing with it but `console.warn`. Now: `_readPeak` (tri-state — `null` is unreadable and **never** evidence of silence) feeds a pure `SignalWatcher` that fires only when the system track has produced nothing *while the mic has proven signal*, that corroboration being the only thing separating a dead capture from "nothing is playing yet". A verdict restarts the capture **in place** (same method — not a fallback) onto `system.partN.wav`, never touching `mic.wav`, and the parts are stitched at stop with a silence pad per gap; `planStitch` derives each part's audio start **backwards from when it stopped**, which self-corrects for SCK's 1.7-3s startup lag where a spawn-time calculation cannot. Failure is survivable by construction — `system.wav` IS part one. Afterwards `measureWavPeak` scans every sample into `manifest.tracks.system.silent`, which drives a red **No system audio** badge and a deterministic warning prepended to the note (not LLM-authored: a summariser handed a one-sided transcript will confidently summarise a monologue). Live, the menu bar replaces the timer with `⚠️ NO SYSTEM AUDIO`. Also shipped: the vault **symlink** fix — `isInsideVault` called `realpathSync` on both sides, so a note in a symlinked vault folder (`Clients/NXT`, `Areas/AIN`, `Projects/Trace`, `Areas/Finances/Wiki`) resolved outside the vault and opened in TextEdit; logical containment is now tried first, realpath second (moved into `vaultLocator.js` to be testable). New gotchas #15/#16, invariant #22, invariant #1 amended. Verified: harness A/B on the installed binary, a real `kill -9` mid-session (mic grew at every 500 ms sample across it), and a zero-filled session driven through to the badge.
